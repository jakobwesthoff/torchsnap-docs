This page is the exhaustive reference for every guest-implemented interface in
the `gadget` world. Each section shows the WIT contract, the SDK trait, and
usage examples. For background on the WIT notation, see the
[WIT Primer](/development/interfaces/).

Every gadget must implement all four export interfaces. For search and
messaging, the SDK provides the typed `Search` and `Messaging` traits, which
implement the generated guest traits for you. It also provides
`impl_noop_messaging!` and `impl_noop_tasks!` macros for interfaces your gadget
doesn't use. Registration is handled by the `define_gadget!` macro:

```rust
use torchsnap_gadget_sdk::prelude::*;

struct MyGadget;
define_gadget!(MyGadget);
```

`define_gadget!` generates the WASM component FFI shims that wire every guest
export to the trait implementations on your struct.

<Aside type="note">
  WASM gadgets execute single-threaded. Your gadget will never handle two host
  calls concurrently. All calls (lifecycle, search, messaging, tasks) are
  serialized by the host.
</Aside>

### Global state

As WASM execution is single-threaded, you can safely use global state without
synchronization primitives. In Rust, the idiomatic pattern is `thread_local!`
with `Cell`, `RefCell`, or `OnceCell` for interior mutability:

```rust
use std::cell::{Cell, RefCell, OnceCell};

thread_local! {
    static CONFIG_CACHE: OnceCell<Config> = const { OnceCell::new() };
    static RESULT_LIMIT: Cell<u32> = const { Cell::new(50) };
}
```

State initialized in `enable()` is available in all subsequent calls
(`entries()`, `search()`, `execute()`, `on_setting_changed()`, etc.) for the
lifetime of the gadget instance.

## Lifecycle

Controls gadget activation, deactivation, and settings change notifications. The
host calls into this interface to manage the gadget's lifetime.

### WIT contract

```wit
interface lifecycle {
  enable: func() -> result<_, string>;
  disable: func();
  on-setting-changed: func(key: string, value: string);
}
```

### SDK trait

```rust
pub trait LifecycleGuest {
    fn enable() -> Result<(), String>;
    fn disable();
    fn on_setting_changed(key: String, value: String);
}
```

### enable()

Runs when the gadget is activated: at startup if the gadget is enabled in
settings, or when the user toggles it on. This is where you initialize state,
open database connections, seed caches from settings, or run first-launch data
imports.

Returning `Err(string)` signals a fatal initialization failure. The host
disables the gadget immediately and logs the error message. No further calls are
dispatched after a failed enable. Only return an error for conditions that
genuinely prevent the gadget from functioning. Non-fatal issues (like a network
fetch failing on first launch) should be handled internally.

```rust
fn enable() -> Result<(), String> {
    let db = sql_storage::connection();
    let count = load_initial_data(&db)?;
    log_info!("Gadget enabled", "entries" => count);
    Ok(())
}
```

### disable()

Runs when the gadget is deactivated. Clean up any state here. The host drops the
WASM instance after this call, so all memory is reclaimed regardless, but
explicit cleanup lets you flush pending work or log a clean shutdown.

```rust
fn disable() {
    log_info!("Gadget disabled");
}
```

### on_setting_changed()

Fires whenever a setting in the gadget's namespace changes. `key` is relative
(the `gadgets.<id>.` prefix is stripped), and `value` is a JSON-encoded string
using the same encoding as
[`settings::get`](/development/interfaces/imports/#settings).

```rust
fn on_setting_changed(key: String, value: String) {
    match key.as_str() {
        "max-results" => {
            if let Ok(limit) = serde_json::from_str::<u32>(&value) {
                RESULT_LIMIT.with(|c| c.set(limit));
            }
        }
        _ => {}
    }
}
```

<Aside type="note">
  The host deduplicates rapid writes to the same key before this callback fires.
  If the user moves a slider quickly and generates many writes, the gadget
  receives one call with the final value, not one per intermediate step. Your
  implementation can unconditionally apply the value it receives without
  debouncing.
</Aside>

## Search

Controls how the gadget provides results and what happens when the user
activates one. This is the most substantial export interface. The
[Search](/development/search/) page covers the concepts (catalog mode, query
mode, prefix routing, custom views) in detail. This section is the type and
function reference.

### WIT contract

```wit
interface search {
  use types.{entry-icon, entry-actions};

  record catalog-entry {
    id: string,
    title: string,
    subtitle: option<string>,
    icon: option<entry-icon>,
    keywords: list<string>,
    actions: entry-actions,
  }

  record scored-entry {
    id: string,
    title: string,
    subtitle: option<string>,
    icon: option<entry-icon>,
    score: u32,
    title-highlight-positions: list<u32>,
    subtitle-highlight-positions: list<u32>,
    actions: entry-actions,
  }

  record view-response {
    view: string,
    data: option<string>,
    results: list<scored-entry>,
  }

  variant search-response {
    nothing,
    results(list<scored-entry>),
    custom-ui(view-response),
    inline-ui(view-response),
  }

  enum post-action { nothing, dismiss, keep-open, open-settings }

  entries: func() -> list<catalog-entry>;
  search: func(query: string, matched-prefix: option<string>) -> search-response;
  execute: func(command: string) -> result<post-action, string>;
}
```

`entry-actions` comes from the shared
[`types`](/development/interfaces/imports/#shared-types) interface.

### SDK trait

```rust
pub trait Search {
    type Command: Serialize + DeserializeOwned;

    fn entries() -> Vec<CatalogEntry<Self::Command>> {
        Vec::new()
    }
    fn search(query: String, matched_prefix: Option<String>) -> SearchResponse<Self::Command>;
    fn execute(command: Self::Command) -> Result<PostAction, String>;
}
```

`Command` is your gadget's own type for what an action does (see
[Commands](/development/search/#commands)). The SDK implements the generated
`SearchGuest` trait for every type that implements `Search`. That
implementation encodes the commands of your entries to JSON on the way out,
and decodes the command string back into `Self::Command` before it calls your
`execute()`.

You can implement `SearchGuest` by hand instead and work with the raw WIT types
and command strings. The prelude does not export it. Import it as
`torchsnap_gadget_sdk::SearchGuest`, and the generated entry types from
`torchsnap_gadget_sdk::wit_search`. A type that implements `Search` cannot also
implement `SearchGuest`.

### Types

The entry, action, and response types below are the SDK's own. They are
generic over the command type `C`, and the prelude exports them.

#### CatalogEntry

Returned by `entries()` for host-side fuzzy matching
([catalog mode](/development/search/#catalog-mode)).

| Field | Type | Description |
|---|---|---|
| `id` | `String` | Unique identifier within this gadget. The host records which entries the user picks by this ID. |
| `title` | `String` | Primary display text. The host highlights match positions. |
| `subtitle` | `Option<String>` | Secondary text shown below the title. |
| `icon` | `Option<EntryIcon>` | Result icon. See [shared types](/development/interfaces/imports/#shared-types). |
| `keywords` | `Vec<String>` | Additional match targets. Keyword matches score the entry but are not highlighted in the title. |
| `actions` | `Actions<C>` | The entry's actions, one optional action per slot. See [Actions](#actions). |

#### ScoredEntry

Returned by `search()` for gadget-scored results
([query mode](/development/search/#query-mode)).

| Field | Type | Description |
|---|---|---|
| `id` | `String` | Unique identifier within this gadget. |
| `title` | `String` | Primary display text. |
| `subtitle` | `Option<String>` | Secondary text. |
| `icon` | `Option<EntryIcon>` | Result icon. |
| `score` | `u32` | Sort ranking. Higher scores appear first. |
| `title_highlight_positions` | `Vec<u32>` | UTF-16 code unit offsets to highlight in the title. |
| `subtitle_highlight_positions` | `Vec<u32>` | UTF-16 code unit offsets to highlight in the subtitle. |
| `actions` | `Actions<C>` | Same semantics as `CatalogEntry`. |

#### Actions

The actions of an entry, one optional field per
[slot](/development/search/#slots). The slot decides the key that runs the
action.

| Field | Type | Key |
|---|---|---|
| `primary` | `Option<Action<C>>` | <kbd>Enter</kbd>, or a click on the entry |
| `secondary` | `Option<Action<C>>` | <kbd>Cmd</kbd>+<kbd>Enter</kbd> |
| `copy` | `Option<Action<C>>` | <kbd>Cmd</kbd>+<kbd>C</kbd> |
| `reveal` | `Option<Action<C>>` | <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> |
| `delete` | `Option<Action<C>>` | <kbd>Cmd</kbd>+<kbd>Backspace</kbd> |
| `open_settings` | `Option<Action<C>>` | <kbd>Cmd</kbd>+<kbd>,</kbd> |

<kbd>Cmd</kbd> is <kbd>Ctrl</kbd> on platforms other than macOS.

| Method | Description |
|---|---|
| `Actions::new()` | No actions. Same as `Actions::default()`. |
| `.primary(label, command)` | Fill `primary` with a labeled action. |
| `.secondary(label, command)` | Fill `secondary` with a labeled action. |
| `.copy(action)`, `.reveal(action)`, `.delete(action)`, `.open_settings(action)` | Fill that slot with `action`. |
| `.iter()` | The filled slots as `(Slot, &Action<C>)` pairs, in the order of the fields above. |

A second builder call for the same slot replaces the first action.

#### Action

| Field | Type | Description |
|---|---|---|
| `label` | `Option<String>` | What the launcher shows. `None` shows the slot's default label, such as "Copy". `primary` and `secondary` have no default and show the entry's title. |
| `command` | `C` | What running the action does. `execute()` receives it when the user runs the action. |

`Action::new(command)` creates an action without a label, and
`Action::labeled(label, command)` one with a label.

#### SearchResponse

| Variant | Description |
|---|---|
| `Nothing` | The gadget has nothing for this query. |
| `Results(Vec<ScoredEntry<C>>)` | Standard scored results merged into the host's result list. |
| `CustomUi(ViewResponse<C>)` | Replaces the entire result list with the named [frontend view](/development/frontend/views/). |
| `InlineUi(ViewResponse<C>)` | Rendered above the result list. Only one gadget can claim the inline slot per search. |

Returning `Results(vec![])` is semantically different from `Nothing`: it tells
the host the gadget participated and explicitly produced zero results, which
clears any stale entries from a previous keystroke.

#### ViewResponse

| Field | Type | Description |
|---|---|---|
| `view` | `String` | Name of the frontend component registered in the [manifest](/development/manifest/#custom-views). |
| `data` | `Option<String>` | JSON-encoded payload forwarded to the React component. |
| `results` | `Vec<ScoredEntry<C>>` | Entries to display in the result list alongside the view. Empty for full-takeover custom UIs. |

#### PostAction

Returned by `execute()` to control launcher behavior after activation.

| Variant | Effect |
|---|---|
| `Nothing` | Leave the launcher open, state unchanged. |
| `Dismiss` | Close the launcher and reset its state. |
| `KeepOpen` | Leave the launcher open. Functionally identical to `Nothing`; exists as a semantic signal for multi-select workflows. |
| `OpenSettings` | Close the launcher and open the Settings window on this gadget's section. A gadget without a settings section of its own gets the Gadgets page. |

### entries()

Returns the gadget's catalog entries for host-side fuzzy matching. Called on
every keystroke. Gadgets that only use query mode can leave it out, as the
default implementation returns an empty `Vec`.

```rust
fn entries() -> Vec<CatalogEntry<Command>> {
    QUOTES.with(|q| {
        q.borrow()
            .iter()
            .map(|quote| quote.to_catalog_entry())
            .collect()
    })
}
```

<Aside type="note" title="Performance">
  `entries()` is called on every keystroke, even though the returned list does
  not depend on the query. For most gadgets this is not a problem, as the data
  passes through the WIT bridge quickly. Should large result sets become a
  bottleneck in the future, a caching mechanism is being considered (for
  example, allowing the gadget to signal "no change since last call" to avoid
  re-transferring the full list). The exact approach has not been decided yet.
</Aside>

### search()

Called on every keystroke with the raw query string. `matched_prefix` is
`Some("=")` (or whichever prefix) when the gadget claimed a
[prefix](/development/search/#prefix-routing) and the user's input starts with
it. `None` otherwise. Gadgets that only use catalog mode return
`SearchResponse::Nothing`.

```rust
fn search(query: String, matched_prefix: Option<String>) -> SearchResponse<Command> {
    let input = match &matched_prefix {
        Some(prefix) => &query[prefix.len()..],
        None => &query,
    };

    match evaluate(input) {
        Some(result) => SearchResponse::Results(vec![result.to_scored_entry()]),
        None => SearchResponse::Nothing,
    }
}
```

<Aside type="tip" title="Keep it fast">
  Responsiveness is one of the most important aspects of a launcher's user
  experience. Both `entries()` and `search()` run on every keystroke, so keep
  them as quick as possible. Avoid costly operations like filesystem scans or
  network requests inside these functions. Instead, move expensive work into a
  [scheduled task](/development/manifest/#scheduled-tasks) that updates cached
  data in the background. The bundled App Launcher gadget, for example, rescans
  installed applications in a periodic task rather than on every keystroke.
</Aside>

### execute()

Runs when the user runs an action. Receives the command of that action,
decoded into your `Command` type. The entry and the slot are not passed. Put
everything the action needs into the command.

A gadget whose entries open or copy a URL, and whose "API token missing" entry
opens its settings:

```rust
fn execute(command: Command) -> Result<PostAction, String> {
    match command {
        Command::OpenUrl(url) => {
            opener::open_url(&url).map_err(|e| format!("open URL: {e}"))?;
            Ok(PostAction::Dismiss)
        }
        Command::CopyUrl(url) => {
            clipboard::write_text(&url).map_err(|e| format!("copy URL to clipboard: {e}"))?;
            Ok(PostAction::Dismiss)
        }
        Command::OpenSettings => Ok(PostAction::OpenSettings),
    }
}
```

If the command string does not decode into `Command`, the SDK returns an `Err`
without calling your `execute()`.

## Messaging

Custom RPC between the gadget's [frontend](/development/frontend/) (React views
and settings panels) and its WASM backend. This interface is optional: only
gadgets with a frontend that needs to communicate with the backend implement it.

### WIT contract

```wit
interface messaging {
  handle-message: func(method: string, payload: string) -> result<string, string>;
}
```

### SDK trait

```rust
pub trait Messaging {
    type Request: DeserializeOwned;

    fn handle(request: Self::Request) -> Result<serde_json::Value, String>;
}
```

`Request` lists every method your frontend calls. The SDK deserializes each
call from an object with a `method` and a `payload` key, so an enum with
serde's adjacent tagging maps each method name to a variant and the payload to
the variant's fields:

```rust
#[derive(Deserialize)]
#[serde(tag = "method", content = "payload", rename_all = "snake_case")]
enum Request {
    GetHistory { page: u32 },
    ClearHistory,
}

impl Messaging for MyGadget {
    type Request = Request;

    fn handle(request: Request) -> Result<serde_json::Value, String> {
        match request {
            Request::GetHistory { page } => {
                let entries = load_history_page(page)?;
                serde_json::to_value(&entries).map_err(|e| format!("serialize history: {e}"))
            }
            Request::ClearHistory => {
                clear_history_db()?;
                Ok(serde_json::Value::Bool(true))
            }
        }
    }
}
```

Methods without arguments are unit variants such as `ClearHistory`. They
accept an empty object or `null` as payload.

The SDK implements the generated `MessagingGuest` trait for every type that
implements `Messaging`, and serializes the `Ok` value as the response.
`Err(String)` propagates to the frontend as an error on the `sendMessage`
promise. An unknown method or a payload that does not fit its variant rejects
the promise as well, before `handle` runs.

### Implementing MessagingGuest by hand

A gadget can implement the generated trait directly instead. The prelude does
not export it. Import it as `torchsnap_gadget_sdk::MessagingGuest`:

```rust
pub trait MessagingGuest {
    fn handle_message(method: String, payload: String) -> Result<String, String>;
}
```

Both `payload` and the `Ok` return value are JSON-encoded strings. The
`method` parameter lets a single gadget expose multiple operations. The
standard pattern is a match on method names:

```rust
fn handle_message(method: String, payload: String) -> Result<String, String> {
    match method.as_str() {
        "get_history" => {
            let request: PageRequest = messaging::parse_payload(&payload)?;
            let entries = load_history_page(request.page)?;
            messaging::to_response(&entries)
        }
        "clear_history" => {
            clear_history_db()?;
            messaging::to_response(&true)
        }
        other => Err(format!("unknown method: {other}")),
    }
}
```

### SDK helpers

The `messaging` module is not in the prelude. Import it with
`use torchsnap_gadget_sdk::messaging;`.

| Function | Description |
|---|---|
| `messaging::decode_request<R>(method, payload)` | Decode a call into `R` the way `Messaging` does. Public so your tests can check your `Request` enum against the payloads your frontend sends. |
| `messaging::parse_payload<T>(payload)` | Parse the JSON-encoded payload into `T`. |
| `messaging::to_response<T>(value)` | Serialize `value` as a JSON-encoded response string. |

### Noop macro

Gadgets that don't use messaging provide a stub with `impl_noop_messaging!`:

```rust
impl_noop_messaging!(MyGadget);
```

This generates an implementation that returns
`Err("gadget does not handle messages: <method>")` for any call.

<Aside type="note">
  Messaging is strictly request/response. WASM gadgets cannot stream data to the
  frontend. Each `sendMessage` call from the frontend produces exactly one
  response or error.
</Aside>

## Tasks

Scheduled background work via cron expressions declared in the
[manifest](/development/manifest/#scheduled-tasks). The host invokes the
gadget's `run_task` export at the configured times. Task errors are logged but
do not disable the gadget.

### WIT contract

```wit
interface tasks {
  run-task: func(task-id: string) -> result<_, string>;
}
```

### SDK trait

```rust
pub trait TasksGuest {
    fn run_task(task_id: String) -> Result<(), String>;
}
```

`task_id` matches the `id` field from the manifest's `[[tasks]]` entry. The
standard pattern dispatches on the ID:

```rust
fn run_task(task_id: String) -> Result<(), String> {
    match task_id.as_str() {
        "refresh-data" => fetch_and_update_cache(),
        "prune-history" => delete_entries_older_than_days(30),
        _ => Err(format!("unknown task: {task_id}")),
    }
}
```

<Aside type="note">
  Tasks are best-effort. Returning `Err(String)` logs the error but does not
  disable the gadget or prevent future task invocations. The host only spawns a
  scheduler loop when the manifest declares at least one `[[tasks]]` entry.
</Aside>

### Noop macro

Gadgets that don't use scheduled tasks provide a stub with `impl_noop_tasks!`:

```rust
impl_noop_tasks!(MyGadget);
```

This generates an implementation that returns
`Err("gadget declares no scheduled tasks: <task_id>")` for any call.
