[WIT](https://component-model.bytecodealliance.org/design/wit.html)
(WebAssembly Interface Types) is the interface definition language of the
[WebAssembly Component Model](https://component-model.bytecodealliance.org/).
Think of it as the equivalent of Protocol Buffers for WebAssembly: it describes
the functions, types, and error shapes that two sides of a boundary exchange,
without prescribing the implementation language on either side.

For Torchsnap, WIT is the single source of truth for the host-gadget boundary.
The host uses it to generate the Rust code that calls into gadgets. Gadgets use
it (through the SDK or directly) to generate the code that implements those
calls and reaches back into the host. Both sides agree on the same types, the
same function signatures, and the same error variants because they are generated
from the same file.

<Aside type="caution" title="Breaking changes before 1.0.0">
  The WIT contract can still change in incompatible ways until the Torchsnap
  1.0.0 release. When it changes, you may need to update your gadget's code
  and rebuild it against the new SDK.
</Aside>

This page covers the WIT syntax itself and how bindings are generated from the
contract. If you are already familiar with WIT and want to jump straight to the
available APIs, see the [Imports](/development/interfaces/imports/) and
[Exports](/development/interfaces/exports/) reference pages, which document
every interface with its WIT definition, SDK helpers, and code examples.

## Worlds

WIT organizes contracts into **worlds**. A world declares which interfaces the
component imports (calls into) and which it exports (implements). The Torchsnap
gadget contract defines a single world called `gadget`:

```wit
world gadget {
  // Host capabilities the gadget can call
  import logging;
  import clipboard;
  import sql-storage;
  // ... (14 imports total)

  // Interfaces the gadget must implement
  export lifecycle;
  export search;
  export messaging;
  export tasks;
}
```

The `import` and `export` lines reference named interfaces defined elsewhere in
the same file. What each interface contains is covered in the sections below.

## Interfaces and functions

An `interface` groups related functions and types. Functions are declared with
`func`, listing their parameters and return type:

```wit
interface clipboard {
  write-text: func(text: string) -> result<_, clipboard-error>;
}
```

This declares a `clipboard` interface with one function, `write-text`, that
takes a string and returns either success or a `clipboard-error`.

## Records

A `record` is a named struct with typed fields:

```wit
record action {
  label: option<string>,
  command: string,
}
```

## Variants

A `variant` is a tagged union. Each case can optionally carry data:

```wit
variant entry-icon {
  hero-icon(string),
  data-url(string),
  asset-icon(string),
  emoji(string),
}
```

Each case names the kind of icon and carries the value (a Heroicons name, a
base64 data URL, a bundled asset path, or an emoji character).

## Enums

An `enum` is a variant where no case carries data:

```wit
enum post-action { nothing, dismiss, keep-open, open-settings }
```

## Resources

A `resource` is an opaque handle with methods. The host creates it, the gadget
holds a reference and calls methods on it:

```wit
resource sql-handle {
  execute: func(sql: string, params: list<sql-value>) -> result<u64, string>;
  query: func(sql: string, params: list<sql-value>) -> result<list<list<sql-value>>, string>;
}
```

The gadget obtains an `sql-handle` by calling `connection()` and then uses
`execute` and `query` on it. The host manages the underlying database connection
behind the handle.

## Built-in types

WIT provides a set of generic types used throughout the contract:

- `option<T>`: a value that may be absent (like Rust's `Option` or
  TypeScript's `T | undefined`)
- `result<T, E>`: success or failure (like Rust's `Result`)
- `list<T>`: a variable-length sequence
- `tuple<T, U>`: a fixed-size pair (or triple, etc.)
- `string`, `bool`, `u8`, `u16`, `u32`, `u64`, `s32`, `s64`, `f64`: scalar
  types

## Cross-interface references

The `use` keyword imports types from another interface so they can be shared:

```wit
interface search {
  use types.{entry-icon, entry-actions};
  // ...
}
```

This allows `search` to reference `entry-icon` and `entry-actions` without
redefining them. The `types` interface exists specifically to hold shared
type definitions used by both imports and exports.

## Generating bindings

The WIT file is language-agnostic. Any language that can compile to
`wasm32-wasip2` and produce a valid WebAssembly component can implement the
gadget contract. What differs between languages is how you turn the WIT
definitions into callable code.

### Rust and the SDK

For Rust, the
[wit-bindgen](https://github.com/bytecodealliance/wit-bindgen) project provides
a procedural macro that reads the WIT file at compile time and generates Rust
traits, structs, and function stubs matching the contract. The
`torchsnap-gadget-sdk` crate runs this generation once:

```rust
// Inside torchsnap-gadget-sdk (gadgets/gadget-sdk/src/lib.rs)
wit_bindgen::generate!({
    path: "wit",
    world: "gadget",
    pub_export_macro: true,
    default_bindings_module: "::torchsnap_gadget_sdk",
});
```

This produces the four guest traits (`LifecycleGuest`, `SearchGuest`,
`MessagingGuest`, `TasksGuest`), all the WIT record and variant types
(`CatalogEntry`, `ScoredEntry`, `SearchResponse`, `EntryIcon`, etc.), and the
host import modules (`clipboard`, `http`, `opener`, and so on).

For search and messaging, the SDK adds typed `Search` and `Messaging` traits
that implement `SearchGuest` and `MessagingGuest` for you, and its own entry
and response types that carry your gadget's command type. Its prelude exports
these together with `LifecycleGuest`, `TasksGuest`, `EntryIcon`, `PostAction`,
the host import modules and the SDK's helper modules, so your gadget code only
needs:

```rust
use torchsnap_gadget_sdk::prelude::*;
```

On top of the raw generated bindings, the SDK adds convenience helpers like
typed settings access, SQL row parsing, and structured logging. These are
covered in the [Imports](/development/interfaces/imports/) reference alongside
the underlying WIT interfaces.

You do not need to run `wit-bindgen` yourself or reference the WIT file directly
when using the SDK. The bindings are pre-generated inside the crate.

### Other languages

<Aside type="note">
  The WIT contract is language-agnostic. If your language has a
  [Component Model bindings generator](https://component-model.bytecodealliance.org/language-support.html)
  (Go, C, C++, JavaScript, and others have varying levels of support), you can
  generate bindings from the WIT file in the SDK repository and implement the
  gadget world directly. The Rust SDK is a convenience layer, not a requirement.
</Aside>

## Full WIT contract

The complete interface definition for the `gadget` world. This is the
source of truth for what gadgets must implement and what the host provides. The
canonical copy lives at
[`gadgets/gadget-sdk/wit/torchsnap-gadget.wit`](https://github.com/jakobwesthoff/torchsnap/blob/main/gadgets/gadget-sdk/wit/torchsnap-gadget.wit)
in the [Torchsnap repository](https://github.com/jakobwesthoff/torchsnap).

<Aside type="note" title="Documentation version: torchsnap:gadget@0.2.0">
  This documentation reflects the `torchsnap:gadget@0.2.0` WIT contract. The
  Rust SDK (`torchsnap-gadget-sdk`) and the TypeScript SDK
  (`@torchsnap/gadget-sdk`) share its version number. The
  pages in this section cannot be automatically generated from the WIT file. While
  we keep them in sync with each release, the canonical WIT file in the SDK
  repository always takes precedence if you notice a discrepancy.
</Aside>
