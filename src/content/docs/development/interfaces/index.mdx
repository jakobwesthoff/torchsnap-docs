Gadgets run inside a sandbox. They cannot call host APIs directly. Instead, the
host and gadget communicate through a set of typed interfaces that define exactly
what the gadget must implement, what capabilities the host offers, and what data
shapes cross the boundary. These interfaces are specified in
[WIT](https://component-model.bytecodealliance.org/design/wit.html)
(WebAssembly Interface Types), the interface definition language of the
WebAssembly Component Model. The [WIT Primer](/development/interfaces/wit-primer/)
covers the notation in detail.

The interfaces are split into two sides. **Imports** are capabilities the host
provides to your gadget: clipboard access, HTTP requests, file I/O, SQLite
storage, and more. **Exports** are interfaces your gadget implements to deliver
results back to the user: search entries, custom views, launcher actions, and
background tasks. This page gives an overview of each. The
[Imports](/development/interfaces/imports/) and
[Exports](/development/interfaces/exports/) reference pages provide the full
type definitions, function signatures, and SDK helpers.

## Exports

Exports are the interfaces your gadget implements. They are split into four
areas: **lifecycle** (activation, deactivation, settings changes), **search**
(catalog entries, query results, execution), **messaging** (custom frontend-to-backend
RPC), and **tasks** (scheduled background work). All four are mandatory, but not
every gadget needs all of them. Unused exports simply return empty data or an
error.

<Aside type="tip">
  If you are writing your gadget in [Rust](https://www.rust-lang.org/) (the
  language all bundled gadgets are written in), the
  `torchsnap-gadget-sdk` crate handles WIT binding generation and provides
  ergonomic helpers on top of the raw interfaces. For unused exports, the
  `impl_noop_messaging!` and `impl_noop_tasks!` macros generate stub
  implementations automatically.
</Aside>

<Aside type="note">
  The code examples below use the Rust SDK for readability. The raw WIT
  interface signatures and type definitions can be found in the
  [Imports](/development/interfaces/imports/) and
  [Exports](/development/interfaces/exports/) reference pages.
</Aside>

### Lifecycle

The host calls into `lifecycle` to activate and deactivate your gadget and to
notify it about setting changes. `enable()` runs when the gadget is turned on
(at startup or when the user toggles it in settings). This is where you set up
state, open database connections, or validate configuration. If `enable()`
returns an error, the host disables the gadget and logs the message. `disable()`
runs on deactivation and is where you clean up. `on_setting_changed()` fires
whenever a setting in your gadget's namespace changes, giving you the key and
its new JSON-encoded value.

```rust
impl LifecycleGuest for MyGadget {
    fn enable() -> Result<(), String> {
        // Initialize state, open connections, validate config
        Ok(())
    }

    fn disable() {
        // Clean up
    }

    fn on_setting_changed(key: String, value: String) {
        // React to configuration changes
    }
}
```

<Aside type="note">
  WASM gadgets execute single-threaded. Your gadget will never handle two host
  calls concurrently. All calls (lifecycle, search, messaging, tasks) are
  serialized by the host.
</Aside>

#### Global state

As WASM execution is single-threaded, you can safely use global state without
synchronization primitives. In Rust, the idiomatic pattern is `thread_local!`
with `Cell`, 
`RefCell`, or `OnceCell` for interior mutability:

```rust
use std::cell::{Cell, RefCell, OnceCell};

thread_local! {
    static CONFIG_CACHE: OnceCell<Config> = const { OnceCell::new() };
    static RESULT_LIMIT: Cell<u32> = const { Cell::new(50) };
}
```

State initialized in `enable()` is available in all subsequent calls
(`entries()`, `search()`, `execute()`, `on_setting_changed()`, etc.) for the
lifetime of the gadget instance.

### Search

Search is the primary interface most gadgets are built around. It controls how
your gadget provides results to the user and what happens when one is activated.
The interface exposes three functions:

#### entries()

[`entries()`](/development/interfaces/exports/#search) is called on every keystroke and returns the gadget's full list of
entries. This is [catalog mode](/development/search/#catalog-mode): the host
takes the list and handles all fuzzy matching, scoring, and highlighting itself.
The gadget does not see the query and does not need to filter anything. This is
the right choice for finite, pre-known datasets like application launchers or
system commands.

<Aside type="note" title="Performance">
  `entries()` is called on every keystroke, even though the returned list does
  not depend on the query. For most gadgets this is not a problem, as the data
  passes through the WIT bridge quickly. Should large result sets become a
  bottleneck in the future, a caching mechanism is being considered (for
  example, allowing the gadget to signal "no change since last call" to avoid
  re-transferring the full list). The exact approach has not been decided yet.
</Aside>

#### search()

[`search()`](/development/interfaces/exports/#search) is also called on every keystroke, but receives the raw query string.
This is [query mode](/development/search/#query-mode): the gadget is responsible
for matching, scoring, and returning only the results relevant to the current
query. This is for dynamic data sources like API lookups, database queries, or
custom matching logic.

#### execute()

[`execute()`](/development/interfaces/exports/#search) runs when the user
activates a result. It receives the full `ScoredEntry` and the `ActionId` of the
triggered action, and returns a `PostAction` that controls whether the launcher
stays open or dismisses.

In query mode, the `ScoredEntry` includes the opaque `data` field exactly as
your `search()` returned it. This is the primary mechanism for passing context
from search to execution: serialize whatever your gadget needs (a URL, a
database key, a computed result) into `data` during `search()`, and deserialize
it in `execute()` without maintaining external state. The host never inspects
or modifies the contents.

In catalog mode, `CatalogEntry` has no `data` field. Use the entry's `id` to
look up context instead.

<Aside type="tip" title="Data in catalog mode">
  Adding a `data` field to `CatalogEntry` is being considered and may be
  available in a future version, allowing the same round-trip pattern for
  catalog entries.
</Aside>

Both modes can coexist in the same gadget. The [Search](/development/search/)
page covers catalog mode, query mode, prefix routing, custom UI responses, and
execution in detail.

<Aside type="tip" title="Keep it fast">
  Responsiveness is one of the most important aspects of a launcher's user
  experience. Both `entries()` and `search()` run on every keystroke, so keep
  them as quick as possible. Avoid costly operations like filesystem scans or
  network requests inside these functions. Instead, move expensive work into a
  [scheduled task](/development/manifest/#scheduled-tasks) that updates cached
  data in the background. The bundled App Launcher gadget, for example, rescans
  installed applications in a periodic task rather than on every keystroke.
</Aside>

### Messaging

Gadgets with a [frontend](/development/frontend/) (custom views or settings
panels) may use `messaging` when their UI needs to communicate with the WASM
backend beyond what the standard search interface provides. This is optional:
many gadgets work fine without it.

Messaging lets you define a fully custom set of operations that the frontend can
trigger on the gadget's backend. Each operation is identified by a `method`
string, so a single gadget can expose as many different actions as it needs:
fetching additional data for a custom view, validating configuration in a
settings panel, clearing a cache, triggering a refresh, or anything else. The
frontend calls `sendMessage(method, payload)`, which routes to the gadget's
[`handle_message()`](/development/interfaces/exports/#messaging) export. Both
the request and response are JSON-encoded strings. This is strictly
request/response; WASM gadgets cannot stream data to the frontend.

```rust
impl MessagingGuest for MyGadget {
    fn handle_message(method: String, payload: String) -> Result<String, String> {
        match method.as_str() {
            "validate_api_key" => {
                let key: String = messaging::parse_payload(&payload)?;
                let valid = verify_api_key_with_remote(&key)?;
                messaging::to_response(&valid)
            }
            "clear_history" => {
                clear_history_database()?;
                messaging::to_response(&true)
            }
            _ => Err(format!("unknown method: {method}")),
        }
    }
}
```

### Tasks

Gadgets that need periodic background work declare
[`[[tasks]]`](/development/manifest/#scheduled-tasks) entries in their manifest
with cron expressions. The host invokes the gadget's
[`run_task()`](/development/interfaces/exports/#tasks) export at the configured
times, passing the task ID from the manifest. Task errors are logged but do not
disable the gadget.

A weather gadget, for example, might refresh its forecast cache every hour so
that search results always show current data without making API calls on every
keystroke. The manifest declares the task with a cron expression:

```toml title="manifest.toml"
[[tasks]]
id = "refresh-forecast"
schedule = "0 * * * *"
```

The host calls `run_task()` with the matching task ID at the top of every hour.
The gadget dispatches on the ID and performs the work:

```rust title="src/lib.rs"
impl TasksGuest for MyGadget {
    fn run_task(task_id: String) -> Result<(), String> {
        match task_id.as_str() {
            "refresh-forecast" => fetch_and_cache_forecast(),
            _ => Err(format!("unknown task: {task_id}")),
        }
    }
}
```

## Imports

Imports are capabilities the host provides. Your gadget calls into them to
interact with the system, read data, or use host services. Gadgets run in a
deny-by-default sandbox: most imports require an explicit
[permission](/development/manifest/#permissions) grant in the gadget's manifest
before they can be used. A few basic interfaces (logging, settings, assets,
platform, path resolver) are always available without any declaration.

### Logging

Lets your gadget emit structured log messages with severity levels and optional
key-value metadata. It also supports timing spans for performance measurement.
Log output is visible in the [Torchsnap devtools panel](/development/devtools/).

<Aside type="tip">Always available. No manifest permission required.</Aside>

```rust
log_info!("Fetching results", "source" => "api");
let span = logging::span_start("api-call", None, &[]);
// ... do work ...
logging::span_end(span, &[("status".into(), "ok".into())]);
```

### Settings

Gives read access to your gadget's configuration values. Keys are scoped to your
gadget's namespace (the `gadgets.<id>.` prefix is stripped automatically), and
values are JSON-encoded strings. The SDK provides typed helpers that parse the
JSON for you.

<Aside type="tip">Always available. No manifest permission required.</Aside>

```rust
let theme: String = settings::get_or("theme", "dark".into());
let max_results: u32 = settings::get_or("max-results", 10);
```

<Aside type="caution" title="TODO: Settings are read-only">
  Gadgets can currently only read settings, not write them programmatically.
  Configuration changes must go through the settings UI. A write API is planned.
</Aside>

### Assets

Lets you read files bundled inside your gadget archive. This is useful for
shipping static data (word lists, icon sets, templates) alongside your WASM
binary. Paths are relative to the gadget's root directory.

<Aside type="tip">Always available. No manifest permission required.</Aside>

```rust
let words = assets::read("data/wordlist.txt")?;
```

### Platform

Detects the host operating system and CPU architecture at runtime. Useful for
gadgets that need to adapt behavior or select platform-specific binaries for
`command` execution.

<Aside type="tip">Always available. No manifest permission required.</Aside>

```rust
use torchsnap_gadget_sdk::platform::{self, Os};

match platform::current_os() {
    Os::Macos => { /* macOS-specific path */ }
    Os::Linux => { /* Linux-specific path */ }
    _ => { /* fallback */ }
}
```

### Path resolver

Resolves [substitution variables](/development/manifest/#substitution-variables)
like `{"${home}"}`, `{"${gadget-data}"}`, and `{"${gadget-archive}"}` to their
actual host paths at runtime. Useful when constructing file paths dynamically.

<Aside type="tip">Always available. No manifest permission required.</Aside>

### Clipboard

Provides write-only access to the system clipboard. This is what most gadgets
use in their `execute()` implementation to copy a result to the clipboard. Read
access is intentionally not exposed for privacy reasons.

Requires permission [`clipboard = true`](/development/manifest/#boolean-flags) in the manifest.

```rust
clipboard::write_text("copied text")?;
```

### Frecency

Lets your gadget query its own frecency ranking data: which items the user
activates most frequently and recently. The host tracks frecency automatically
during execution; this import only controls whether your gadget can read back
that data to drive its own UI (for example, to sort a custom view by usage
frequency).

Requires permission [`frecency = true`](/development/manifest/#boolean-flags) in the manifest.

### SQL storage

Gives your gadget an isolated SQLite database. The host creates the database
file and runs migrations declared in the manifest's
[`[storage.sql]`](/development/manifest/#sql-storage) section before your
gadget's `enable()` is called. You obtain a connection handle and issue queries
through it.

Requires a [`[storage.sql]`](/development/manifest/#sql-storage) section in the manifest declaring the migration files.

```rust
let db = sql_storage::connection();
db.execute("INSERT INTO history (text, timestamp) VALUES (?, ?)", &[
    SqlValue::Text(entry.to_string()),
    SqlValue::Integer(now as i64),
])?;
```

### HTTP

Provides a synchronous HTTP client. The interface supports all standard methods,
custom headers, request bodies, timeouts, and response size limits.

Requires permission [`[permissions.http]`](/development/manifest/#http) in the manifest.

```rust
let response = http::fetch(&HttpRequest {
    url: "https://api.example.com/search?q=test".into(),
    method: HttpMethod::Get,
    headers: vec![],
    body: None,
    timeout_ms: Some(5000),
    max_body_size: None,
    insecure_tls: false,
})?;
```

### Filesystem

Provides read-only access to files on the host filesystem. You can read file
contents, check whether a file exists, and query metadata like size and
modification time.

Requires permission [`[permissions.fs]`](/development/manifest/#filesystem) in the manifest.

### Opener

Opens URLs in the default browser, launches files with their default
application, or reveals files in the system file manager.

Requires permission [`[permissions.opener]`](/development/manifest/#opener) in the manifest.

### Command

Runs system processes and captures their output. You provide the binary path,
arguments, optional stdin, and environment variables, and receive the exit code,
stdout, and stderr. Commands are executed directly without a shell wrapper.

Requires permission [`[[permissions.command]]`](/development/manifest/#command-execution) in the manifest.

### Website metadata

Looks up website titles, descriptions, and favicons through a host-managed cache
shared across all gadgets. Useful for gadgets like bookmark managers or link
aggregators that want to display rich metadata for URLs.

Requires permission [`website-metadata = true`](/development/manifest/#boolean-flags) in the manifest.
